# Anki 制卡原则

生成和审查卡片时，以本文件的内容质量规则为准。规则主要参考 [SuperMemo 的知识表述原则](https://www.supermemo.com/en/blog/twenty-rules-of-formulating-knowledge)、[Michael Nielsen 的长期记忆实践](https://augmentingcognition.com/ltm.html) 和 [Anki 官方手册](https://docs.ankiweb.net/editing.html#effective-learning)。[Junyu 的中文整理](https://junyu25.github.io/posts/2805751/) 与[知乎中文译文](https://zhuanlan.zhihu.com/p/65131722)帮助理解前两篇文章；有疑问时以原文和官方手册为准。

这里的“主动回忆”是指：复习时先看问题，自己想出答案，再翻面核对。必须先理解内容，才适合用这种方式记忆。

## 先理解整体，再拆卡

制卡前先用一小段话说明材料要解决什么问题、主要概念之间有什么关系。这个说明帮助理解材料，不直接制成一张“总结全文”的卡。

从支撑后续理解的基础知识开始，再加入更复杂的判断和应用。基础知识即使简单，只要忘记它会妨碍后续理解或经常导致错误，就值得制卡；人人都知道、忘记也不影响实际工作的常识仍然不制卡。

## 哪些知识值得做卡

对每个准备制卡的知识点依次回答以下问题。任一项不通过，就不制卡或标为 `needs_review`：

1. 它会帮助哪个学习目标、项目，或哪种经常要做的判断？
2. 用户是否已经理解，能否不用原句解释它为什么成立、什么时候不成立？
3. 不查资料就能想起它，是否会让实际工作做得更好，而不只是帮助复述材料？
4. 它是否经常要用、忘记后果严重，或能帮助理解多个相关问题？
5. 信息是否会随时间变化；相关版本、成立条件、作者立场和研究限制是否写清？
6. 是否能找到材料原文，并在需要时找到用来核对的一手资料？
7. 是否能写成一个单独看得懂、只问一件事、答案可以核对的问题？
8. 现有卡片是否已经在问同一件事？

默认拒绝：常识、忘记也不会造成实际问题的小细节、工具用途的直接对应、清单题、课程安排、示例中的临时名字、临时状态、孤立冷知识、长摘要，以及使用时查一下更划算的内容。不设置最低张数。

学习记录、目录、摘要和自检结果只证明“学过什么”，不能证明知识已被充分解释。它们只能帮助找到完整材料；应继续读取完整课程、原文或技术资料。找不到原材料时允许产出 `0` 张卡，不根据标题和提纲补写答案。

`selection_reason` 必须写明卡片会在哪个场景有用、会避免什么问题，或会帮助理解什么知识；只写“很重要”或“课程重点”不算理由。

## 核对事实

- 用户材料告诉我们可以记什么，但其中的说法不一定准确。先理解材料，再核对容易出错或会明显影响实际结果的结论。
- 语言、命令、库、协议和文件格式的实际行为，优先查官方手册、正式规范或维护者文档；研究结论优先查原论文及其补充材料；会随时间变化的事实查当前官方来源。
- 重要原理、容易混淆的成立条件、版本差异、教材中的可疑说法，以及用户明确要求核实的内容，必须用一手资料核对。可以运行一个最小实验来验证行为，但实验不能说明所有适用条件，仍要查规范。
- 材料与一手来源冲突时，答案以一手来源为准，并在 `extra` 或不制卡的理由中记录教材做了什么简化或哪里有误。
- `source` 既要写材料中的具体位置，也要写用来核对事实的一手来源。证据不够时使用 `needs_review`，不要把猜测写成确定事实。

## 优先记什么

优先针对真实任务中需要做选择或容易出错的地方提问，例如数据输入、错误处理、并发、资源清理、进程身份，以及密钥等敏感信息的泄露。基础原理只有在能解释多个真实行为时才优先制卡；答案应解释“为什么”，而不只给命令。

一张好卡只讲清一个能用于多个场景的原理，以及会改变答案的必要条件。不要靠塞入多个命令、选项或步骤来显得内容多。同一个原理换一个示例，不需要再做一张卡。

命令、调试和操作流程还需要真实练习。卡片只用来记使用时机、关键选择和容易犯的错误；不要把完成整项操作所需的步骤全部塞进卡片，也不要把“记得命令”当成“已经会熟练使用”。

## 一张卡只问一件事

这就是常说的“问题原子化”：每张卡只要求给出一个可以明确判断对错的答案。如果一题中的两部分可能一对一错，就拆开；这样答错时能立刻知道自己错在哪里。

不要为了拆得更小，把实际要一起使用的知识拆成没有用途的零件。例如，用户已经知道 `ln` 命令时，没有必要再单独问“哪个命令用于创建链接”；应直接问软链接选项或参数顺序。基础卡都已掌握后，如果一个完整任务仍经常需要使用，可以再保留一张综合应用卡。

## 把清单题改成实际问题

教学框架只是整理材料的方式。真正值得记住的是其中会改变实际做法的知识：

- 把“四遍法的顺序是什么”改为“接手一个由很多函数组成的 Bash 部署脚本时，为什么先从 `main` 或顶层入口追踪执行路径？”
- 把“六层脚本骨架是什么”改成具体问题，例如“一个结尾无条件调用 `main \"$@\"` 的 Bash 脚本被 `source` 时，会发生什么？”
- 把“四类调试手段是什么”改成容易造成严重后果的具体问题，例如“调试含令牌的 Bash 脚本时，为什么 `set -x` 可能泄露密钥？”；如果一个条目只是在说明工具用途，就不制卡。

## 只看问题检查

复习时首先只能看到 Front。每个 Basic Front 按以下顺序写：

1. **背景**：写明在说哪种技术、哪篇资料或哪个作者，以及正在完成什么实际任务。命令题要明确运行环境或工具，例如“在 Bash 数据库迁移脚本中，用 `grep` 检查迁移文件名是否已记录”。
2. **必要信息**：只保留回答问题需要的输入、错误现象、适用条件或对比项；不要把答案或明显提示写进问题。
3. **一个问题**：只问一个原因、条件、区别、命令选择或反例。

把卡片打乱并隐藏 Back、Extra、Source 后，逐张回答：

- 我能否仅凭 Front 看出它在说哪种技术、哪个工具或哪篇资料？
- 我是否知道这道题与哪个实际任务或哪位作者的观点有关？
- 我能否说清这张卡只要求我回答什么？
- 我是否必须自己想出答案，而不是从问题里的提示猜出来？

任一答案为否，就补充背景或拆卡。通过后再删掉多余文字：逐段删除，直到再删就会让技术主题、任务、条件或问题变得含糊。目标是写出最短但完整的问题，不是一味追求字数少。

课程材料在问题中写知识主题和实际应用，例如“在 Bash 数据库迁移脚本中”；课次、阶段号、日期、文件名和章节号只放在 `source`。`source` 用来查原文，不能代替问题中的背景。优先使用材料中真实出现的项目和问题；不要编造用户的经历或私人信息。

### 对照示例

弱：`迁移记录每行一个文件名。如何避免 1.sql 被 grep 误匹配到 11.sql？`

强：`在 Bash 数据库迁移脚本中，用 grep 检查文件名是否已记录时，怎样避免 1.sql 被误判为匹配 11.sql？`

弱：`脚本会执行 curl Authorization 时，为什么不应盲目运行 bash -x？`

强：`调试会处理令牌或密码的 Bash 脚本时，使用 set -x / bash -x 有什么泄露风险？`

弱：`在第 12 课中，grep -x 解决什么问题？`

强：`在 Bash 脚本中用 grep 判断一行是否等于目标字符串时，-x 改变了什么匹配条件？`

## Back 与 Extra

- `back` 直接回答 Front，只保留结论和会改变答案的条件。能用一句话，或一个命令加一句解释说清时，不写成长段。
- `extra` 保存推理过程、反例、适用条件、版本差异、证据说明和容易混淆的情况；不重复 Back。
- Basic 一张只问一件事。包含多个问题、多个条目或多个步骤时，应拆成多张卡。
- Cloze 只用于短定义、公式或固定限制条件，每张 1 至 2 个空。挖空后的句子必须单独看得懂，也不能因为周围文字已经暗示答案而变成猜词题；不要把尚未理解的原句直接复制成 Cloze。
- 判断题通常改问原因、成立条件、例子或反例。只回答“是”或“否”很容易猜中，也不能暴露理解缺口。
- 两个概念容易混淆时，优先问它们的区别、各自适用条件或反例。不要只换一个例子，就为同一原理重复制卡；也不要制作问题几乎相同、答案只差一个词的卡。

## 复习时怎样改卡

以 Anki 中当前显示的内容为起点，不以发布前的 JSON 或来源仓库副本为准。先说明复习时遇到的具体困难，再作最小必要修改：

- 看不出问题在说什么：补上技术、工具、实际任务和会改变答案的条件，直到离开原材料也能理解。
- 问题太长：删除不影响理解和回答的叙述，但不能删掉必要背景。
- 答案难以核对：把直接答案放在最前面，只保留会改变答案的条件；解释、反例和证据放到 Extra。
- 一张卡问了几件事：让原卡只保留最重要的一个问题；其他确实值得记的内容按新卡流程审核，不能顺手添加。
- 事实或成立条件可疑：回到原材料和一手资料核实。来源用于核对，不要求把 Anki 中的新措辞写回仓库。
- 知识不值得继续记：优先暂停，而不是为了保留卡片勉强改写。

修改前后都要重新做“只看问题检查”。写入前向用户展示原内容、修改内容和改动理由，只更新用户确认的 note。

## 按来源取舍

### 会话、笔记与课程

保留能用于其他场景的原理、判断条件、反例，以及选择某种做法的原因。Front 写清技术、工具、系统或真实任务；课程编号和学习日期只写入 `source`。临时排障步骤、待办和当时环境状态留在笔记。

### 文章与网页

在 `learning_goal` 中说明阅读目的。观点卡要在 Front 中写明作者或文章；`source` 保存 URL、标题、小节或其他查找线索。文章中的修辞性表达、标题和摘要不直接制卡。

### 论文与技术资料

第一次阅读只为术语、研究问题、方法、主要观点和限制制作少量基础卡；以后深入阅读时，只补将来还会用到的证据、常见失败、适用条件和方法比较。Front 写明论文、作者或方法名，不把只在特定研究条件下成立的结论写成普遍事实。

## 优先级和发布前检查

- `1`：能用于多个场景的重要原理、经常需要的判断，或忘记后果严重的知识。
- `2`：重要实践原则、常见错误和常见干扰点。
- `3`：低频细节，默认 `draft` 或 `needs_review`。
- `4`：默认 `rejected`，不进入发布。

发布前逐张确认：这条知识值得记，问题单独看也能理解，事实已经核对；Back 简短且只回答一件事；Source 能找到原文；Anki 现有卡片没有在问同一件事。程序没有报错或警告，并不代表卡片一定清楚、有用、正确，仍要逐张阅读。
