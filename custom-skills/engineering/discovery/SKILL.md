# 需求澄清

## 何时使用

- 同一个词在需求、代码和文档中表示不同意思。
- 两种以上做法都合理，但选择会改变对外行为、数据处理、权限或后续维护。
- 需要判断一个词是否值得写入 `CONTEXT.md`，或一个决定是否值得写 ADR。

如果只是缺少一个能从仓库或一手资料查到的事实，先查资料，不要让用户回答本可以自行查清的问题。

## 怎么做

1. 只读取与当前问题有关的项目说明、代码、规格和任务，列出已经确认的事实、仍是猜测的内容和必须由用户决定的问题。
2. 对每个必须决定的问题给出少量可行选项、推荐项和推荐理由。只有答案会改变范围、对外接口、数据或权限时才询问用户。
3. 整理术语时，先查它在需求、界面、代码和现有文档中的真实用法，优先采用用户和项目成员已经在用的说法。用具体的正常情况和失败情况检查名称是否清楚；没有真实用户时，不要编造用户或使用场景。
4. 只有一个词同时满足以下条件时才写入 `CONTEXT.md`：只在这个项目中有特定含义、会在多个任务中使用，而且不用定义就容易与另一个概念混淆。一般工程术语、类名、配置键、命令和内部处理阶段应留在代码或维护说明中。
5. 新名称应该能用一句普通话解释清楚，不能依赖另一组新造的词。英文标识符本身更准确时保留原样，并在第一次出现时说明用途。
6. 当前澄清涉及的 `CONTEXT.md` 条目不再符合上述条件时，更新或删除它们。难以撤销、存在明显取舍且以后需要解释的决定才写 ADR；其他内容留在当前规格或任务中。

## 输出和限制

先在答复中说明已确认内容、用户决定、未决问题、影响和下一步。已有 PRD 时把已经确认的需求和决定更新到 `.scratch/<feature>/PRD.md`；需要长期使用的术语或决定按上述规则更新项目文档。保存或更新文件后，在答复中说明路径和内容变化。

不要因为正在澄清需求就修改代码或外部任务。查不到的内容写成未知，不要补一个看似完整的答案；只有测试方式会改变对外行为、数据安全或成本时才询问用户。
