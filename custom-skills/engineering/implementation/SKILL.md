# 实现改动

## 怎么做

1. 先看用户要求、相关代码和当前工作树。已有 PRD、任务、`CONTEXT.md` 或 ADR 时只读取有关部分，并保留其他人的改动。
2. 明确这次要改什么、怎样算完成，以及有哪些需要特别小心的地方。没有 PRD 或任务文件也可以直接做；只有不同理解会改变结果时才转去澄清。
3. 写代码前先检查这项功能是否真的需要新增、仓库里是否已有类似实现、标准库或平台能力是否够用，以及现有依赖能否解决。都不够时才增加最少的新代码。
4. 完成一项从输入到结果都能验证的改动。改变对外接口时，同时更新已知调用方并说明迁移办法；采用简单实现时，只在确有上限时记录何时需要升级。
5. 新增或修改了用户、调用方能看到的行为，或者缺陷容易再次出现时，优先在现有测试中补一个能在旧代码上失败的用例。纯文档、文案、注释、元数据、文件清单和简单配置修改不新增单元测试；不要为小改动新建测试框架、辅助层或大量模拟对象。先运行最接近的现有检查，只有项目规则或改动风险需要时才扩大范围。
6. 最后查看 diff，确认没有带入无关修改。当前工作由本地任务文件驱动时，按实际进度更新状态、结果和剩余问题，并在交付中说明；只报告这次真正运行并看过结果的检查。

## 交付和限制

说明改了哪些文件、行为有什么变化、运行了哪些检查，以及还有什么没有解决。不会自行执行 `git add`、`commit` 或 `push`，也不会发布或通知外部系统；用户已经明确要求这些动作时，执行前检查目标和暂存内容。

不要用占位代码或悄悄忽略错误来假装完成。不能只看行数，也不能为了少写代码删掉必要的输入检查、防止数据丢失的处理、安全措施、无障碍要求或用户明确要求的行为。检查失败时，说明失败原因和目前完成到什么程度。
