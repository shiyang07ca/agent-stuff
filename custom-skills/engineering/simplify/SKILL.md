# 简化实现

目标是在保持当前必要行为和明确接口要求的前提下，降低理解、修改和验证整个实现所需的复杂度；不以代码行数、文件数或类型数最少为目标。

## 范围和模式

- 先确定用户要求、待检查的 diff 或版本，以及允许修改的文件。用户只要求审查、分析或建议时，仅做消融推演；用户要求简化或执行实验时，才修改工作区。
- 只检查本次改动引入、使其成为必要条件或明显复杂化的结构。附近既有问题不因被看到而进入范围。
- 实现应当已经基本工作。缺少或失败的基线检查不妨碍只读审查，但在无法区分实验影响时不实际修改。

## 确定必须保持的内容

阅读相关需求、目标差异、调用方和检查，区分：

- 必须保持的可观察行为，以及公共 API、数据格式、协议、安全、无障碍、并发、事务、生命周期和已确认的性能要求；
- 只是当前实现方式的内部调用、模块划分、测试组织和扩展结构。

现有测试和调用方是证据，不自动成为不可改变的要求。不要为了让删除通过而削弱行为断言；测试只锁定私有实现时，可以在保持可观察行为且属于当前范围的前提下更新。删除看似未使用的内容前，检查配置、注册、反射、序列化、框架约定、动态加载和外部消费者。

## 形成消融假设

优先检查以下证据明确的候选：

- 没有独立规则、只做转发的间接层；
- 当前没有使用者的配置、可变性或扩展入口；
- 重复的数据表示、转换或状态；
- 只服务假想未来需求的兼容分支和默认行为；
- 与仓库现有能力平行的新机制，以及由这些结构产生的无用注册和导出。

不要按设计模式名称、实现数量或消费者数量单独判断。把必须一起变化才能得到有效结果的符号视为一个最小消融单元，并为每个单元写清：

1. 它当前解决的具体问题和证据；
2. 准备删除、内联、合并或收敛什么；
3. 哪些检查能够证明必要行为保持；
4. 预计减少的实际复杂度，例如分支或配置状态、调用间接性、表示转换、依赖、需要理解的概念或修改范围。

只有移除后不会把复杂度转移到别处、复制规则或破坏有意义的领域与外部系统边界时，候选才成立。优先删除、内联、合并和收敛；替代结构只有在能够明确降低总复杂度时才引入。

## 审查或实验

审查模式下，推演最小改法，指出准确位置、影响和所需验证，不修改工作区。把有证据的简化建议、仍有当前价值的结构和因信息不足无法判断的候选分开；不要把个人风格偏好报告成问题。

修改模式下：

1. 先检查工作树，确认实验不会覆盖用户已有改动；无法隔离重叠修改时跳过并报告。
2. 首次消融前，选择足以覆盖本次必须保持行为的最小检查集，运行并记录命令和结果作为基线。只有能够确认失败原本存在且与当前改动无关时才带着失败继续；否则停止修改并转为只读审查。
3. 一次只修改一个最小消融单元，运行与它最相关的行为检查，并确认所选复杂度确实下降。
4. 检查失败或收益不成立时，只撤回本次实验产生的具体修改；不要用 `git reset`、`git checkout --` 或 `git stash` 恢复整个文件或工作树。
5. 成功删除后检查同一设计决定产生的关联结构是否也失去用途，但不扩大到无关旧代码。
6. 所有消融单元处理完成后，在最终状态重新运行同一组基线检查，再按仓库要求和修改风险运行更大范围的检查；读取完整结果后检查最终 diff。

当进一步修改会改变必要行为、破坏明确接口要求、需要大范围重构、无法可靠验证或只是换一种写法时停止。

## 交付

审查模式按候选说明位置、当前成本、建议的最小变化、保持或受影响的行为，以及需要补充的验证。修改模式说明实际移除和保留的内容、基线与最终检查结果及未确认事项。没有安全且收益明确的简化时，保持实现不变并说明依据。
