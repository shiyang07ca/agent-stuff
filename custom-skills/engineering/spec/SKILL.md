# 研发规格

## 目标

规格要让实现者知道问题是什么、需要完成什么、哪些内容不做，以及怎样判断结果正确。不要把规格写成很长的使用场景清单，也不要在这里拆实现任务。

## 怎么做

1. 只读取与需求有关的项目说明、代码、现有规格和决定。分清用户已经确认的目标、仓库中能查到的事实、仍是猜测的内容和还没有决定的问题。
2. 写清问题、目标、不做什么和修改范围：保留什么、修改什么、新增什么，以及哪些文件或行为不碰。
3. 需求包含多个可以分别完成和验证的功能时，用简短的功能分组说明它们各自负责什么、谁依赖谁；只有一个功能时直接写要求，不增加多余层级和编号。
4. 对每组要求写清正常行为和用户能看到的结果。配置、权限、状态变化、失败情况、输入输出、调用方、数据限制、并发和兼容性只写与当前需求有关的内容，不为不存在的问题增加章节。
5. 只有具体用户目标能帮助理解需求时才写少量使用场景；没有真实用户时，不要编造用户或使用场景。实现决定、替代方案、迁移和恢复办法也只在确实需要时写。
6. 为关键要求写明怎样验证，可以是测试、命令、实际操作或人工检查。不要把尚未实现的内容写成已经通过。

## 输出

用户要求生成或更新规格时，默认写入 `.scratch/<feature>/PRD.md`。已有文件先合并仍然有效的内容；无法判断应该保留哪一版时，再询问用户。

默认结构：

1. `问题`
2. `目标与不做的内容`
3. `修改范围`
4. `要求`
5. `验证`

只有确实需要时才增加 `功能分组`、`接口和必须遵守的规则`、`使用场景`、`实现决定`、`迁移与恢复`、`风险与待决定事项`。正文使用中文，API、字段、状态值、协议和文件名保持原样。

不要直接发布到外部任务系统，也不要在写规格时创建实现分支或提交。规格必须能回答“为什么做、做什么、不做什么、如何知道做对了”；未知内容直接标明，不要用占位答案补齐篇幅。
